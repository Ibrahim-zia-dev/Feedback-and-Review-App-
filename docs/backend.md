# Feedback & Review App Backend Schema

**Status:** Draft  
**Backend:** Firebase Authentication, Cloud Firestore, Cloud Functions  
**Source documents:** [PRD](docs/PRD.md), [TRD](docs/TRD.md), [App flow](docs/appflow.md)  
**Last updated:** 2026-08-31

## 1. Backend Overview

The MVP uses Cloud Firestore in Native mode. Firestore does not use SQL tables, primary keys, or foreign keys in the relational sense, so this document defines equivalent concepts:

- A **collection** is the equivalent of a table.
- A document ID is the **primary key**.
- A stored `...Id` field is a logical **foreign key**.
- Firestore Security Rules and Cloud Functions enforce relationship integrity because Firestore does not enforce foreign keys automatically.
- Organization-owned records are tenant-scoped and must contain `organizationId` either directly or in their parent path.

The backend must never trust a role, user ID, organization ID, ownership field, status, or timestamp supplied by an untrusted client.

## 2. Firebase Services

| Service | Responsibility |
|---|---|
| Firebase Authentication | Email/password identity, ID tokens, password reset, email verification policy, and session state. |
| Cloud Firestore | Users, organizations, memberships, contexts, assignments, responses, activity, and derived aggregates. |
| Cloud Functions for Firebase | Invitations, role changes, trusted multi-document operations, aggregate maintenance, and scheduled cleanup. |
| Firebase App Check | Reduce abuse from unrecognized clients; not a replacement for authorization. |
| Firebase Analytics | Product events without response text or sensitive data. |
| Crashlytics | Mobile crash monitoring without feedback content. |
| Firebase Cloud Messaging | Optional notifications after MVP notification behavior is approved. |
| Emulator Suite | Local Auth, Firestore, Functions, and Security Rules testing. |

## 3. Naming and Type Conventions

| Logical type | Firestore type | Constraints |
|---|---|---|
| ID | string | Non-empty, generated by Firebase or the application; never user-editable. |
| Text | string | Explicit maximum length per field; trim surrounding whitespace. |
| Integer | number | Whole number; validate range server-side. |
| Boolean | boolean | Use false/true, not nullable flags unless absence has a defined meaning. |
| Timestamp | timestamp | Server timestamp for authoritative fields; store UTC. |
| Enum | string | Validate against documented allowed values. |
| List | array | Bounded item count and item size. |
| Map | map | Bounded keys and values; never accept arbitrary unvalidated maps. |
| Nullable | type or null | Use only where the lifecycle explicitly allows absence. |

Common rules:

- All documents use camelCase field names.
- All server-created records have `createdAt` and `updatedAt` unless explicitly noted.
- All mutation records use server timestamps.
- IDs are opaque; clients must not infer permissions from ID format.
- Text is bounded and normalized for length and surrounding whitespace.
- Do not exceed Firestore document size limits.

## 4. Collection and Key Design

```text
users/{uid}
organizations/{organizationId}
organizations/{organizationId}/members/{uid}
organizations/{organizationId}/contexts/{contextId}
organizations/{organizationId}/contexts/{contextId}/questions/{questionId}
organizations/{organizationId}/contexts/{contextId}/assignments/{assignmentId}
organizations/{organizationId}/responses/{responseId}
organizations/{organizationId}/activity/{activityId}
organizations/{organizationId}/aggregates/{aggregateId}
invitations/{invitationId}
```

Subcollection paths provide a tenant boundary. The repeated `organizationId` field remains required on organization-owned documents for queryability and rule validation.

### Primary key strategy

- `users`: Firebase Auth UID is the document ID.
- `members`: Firebase Auth UID is the document ID, giving one membership per user per organization.
- `organizations`, `contexts`, `questions`, `assignments`, `activity`, and `aggregates`: autogenerated Firestore IDs unless a deterministic ID is specified.
- `responses`: deterministic ID based on `contextId` and `contributorUid`, or a transaction-protected unique submission marker.
- `invitations`: autogenerated ID; store only a hash of an acceptance token, never a reusable raw token.

## 5. Schema Definitions

### 5.1 `users/{uid}`

One document per Firebase Auth user. This is a profile, not an authorization source.

| Field | Type | Required | Default / constraints | Ownership |
|---|---|---:|---|---|
| `uid` | string | Yes | Must equal document ID and `request.auth.uid` | Server |
| `displayName` | string | Yes | 1-100 characters | User may update own value |
| `email` | string | Yes | Auth-provider email, normalized lowercase | Auth provider/server |
| `emailVerified` | boolean | Yes | Mirrors Auth state when refreshed | Server |
| `onboardingCompletedAt` | timestamp/null | No | Null until privacy onboarding completes | Allowed onboarding flow |
| `createdAt` | timestamp | Yes | Immutable server timestamp | Server |
| `updatedAt` | timestamp | Yes | Server timestamp | Server |
| `lastActiveAt` | timestamp/null | No | Updated sparingly | Server |

**Primary key:** `uid`.  
**Relationships:** one user has many memberships and many responses.

### 5.2 `organizations/{organizationId}`

| Field | Type | Required | Default / constraints | Ownership |
|---|---|---:|---|---|
| `organizationId` | string | Yes | Must equal document ID | Server |
| `name` | string | Yes | 2-120 characters | Owner via Function |
| `slug` | string | Yes | Normalized; unique if lookup is enabled | Server |
| `status` | enum | Yes | `active \| suspended \| deleted` | Owner/Function |
| `ownerUid` | string | Yes | Must reference active owner membership | Server |
| `timezone` | string | Yes | IANA timezone | Owner |
| `defaultVisibility` | enum | Yes | `identifiable \| organization_only` | Owner |
| `retentionDays` | integer/null | No | Positive bounded integer or null | Owner |
| `createdAt` | timestamp | Yes | Immutable | Server |
| `updatedAt` | timestamp | Yes | Server timestamp | Server |

**Primary key:** `organizationId`.  
**Relationships:** one organization has many members, contexts, assignments, responses, activity records, and aggregates.

### 5.3 `organizations/{organizationId}/members/{uid}`

Membership and role. This is the source of truth for Firestore access.

| Field | Type | Required | Allowed values / constraints | Ownership |
|---|---|---:|---|---|
| `uid` | string | Yes | Must equal document ID | Server |
| `organizationId` | string | Yes | Must equal parent organization ID | Server |
| `role` | enum | Yes | `contributor \| reviewer \| administrator \| owner` | Owner via Function |
| `status` | enum | Yes | `invited \| active \| suspended` | Owner via Function |
| `displayName` | string | Yes | Profile snapshot | Server |
| `email` | string | Yes | Normalized snapshot; restrict exposure | Server |
| `scopeContextIds` | array<string> | No | Required for scoped reviewers; bounded | Owner/admin via Function |
| `invitationId` | string/null | No | References invitation while invited | Server |
| `joinedAt` | timestamp/null | No | Set when status becomes active | Server |
| `createdAt` | timestamp | Yes | Immutable | Server |
| `updatedAt` | timestamp | Yes | Server timestamp | Server |

**Primary key:** composite `organizationId + uid`, represented by the subcollection path.  
**Foreign keys:** `uid -> users.uid`; `scopeContextIds[] -> contexts.contextId`; `invitationId -> invitations.invitationId`.  
**Invariant:** a Function must prevent removing or suspending the last owner.

### 5.4 `organizations/{organizationId}/contexts/{contextId}`

A task, course, service, event, or other experience being reviewed.

| Field | Type | Required | Allowed values / constraints | Ownership |
|---|---|---:|---|---|
| `contextId` | string | Yes | Must equal document ID | Server |
| `organizationId` | string | Yes | Must equal parent ID | Server |
| `title` | string | Yes | 2-160 characters | Admin/owner |
| `description` | string | Yes | 1-2,000 characters | Admin/owner |
| `type` | enum | Yes | `task \| course \| service \| event \| other` | Admin/owner |
| `status` | enum | Yes | `draft \| active \| paused \| closed` | Admin/owner/Function |
| `ownerUid` | string | Yes | Active permitted member | Admin/owner |
| `visibility` | enum | Yes | `identifiable \| organization_only` | Admin/owner, subject to policy |
| `startAt` | timestamp/null | No | UTC | Admin/owner |
| `endAt` | timestamp/null | No | UTC; must be >= `startAt` | Admin/owner |
| `questionSetVersion` | integer | Yes | MVP fixed at 1 | Server |
| `createdByUid` | string | Yes | Authenticated creator | Server |
| `createdAt` | timestamp | Yes | Immutable | Server |
| `updatedAt` | timestamp | Yes | Server timestamp | Server |
| `closedAt` | timestamp/null | No | Set when closed | Server |

**Primary key:** composite `organizationId + contextId`.  
**Foreign keys:** `ownerUid -> members.uid`; `createdByUid -> members.uid`.  
**Invariant:** only active contexts accept new responses; paused and closed contexts remain readable for existing history.

### 5.5 `.../contexts/{contextId}/questions/{questionId}`

Question metadata for future extensibility. MVP creates a fixed set and does not expose a general form builder.

| Field | Type | Required | Allowed values / constraints | Ownership |
|---|---|---:|---|---|
| `questionId` | string | Yes | Must equal document ID | Server |
| `organizationId` | string | Yes | Must equal parent organization ID | Server |
| `contextId` | string | Yes | Must equal parent context ID | Server |
| `key` | string | Yes | `rating \| review \| suggestion`; unique per context | Server |
| `type` | enum | Yes | `rating_1_to_5 \| long_text` | Server |
| `label` | string | Yes | Bounded display label | Admin within allowed values |
| `required` | boolean | Yes | Rating true; text false in MVP | Server |
| `position` | integer | Yes | Non-negative order | Server |
| `maxLength` | integer/null | No | Required for text questions | Server |
| `active` | boolean | Yes | Immutable after responses unless versioned | Admin/owner |
| `createdAt` | timestamp | Yes | Immutable | Server |
| `updatedAt` | timestamp | Yes | Server timestamp | Server |

**Primary key:** composite `organizationId + contextId + questionId`.  
**Foreign key:** `contextId -> contexts.contextId`.

### 5.6 `.../contexts/{contextId}/assignments/{assignmentId}`

Associates a contributor or reviewer with a context. Explicit assignments avoid unbounded member arrays.

| Field | Type | Required | Allowed values / constraints | Ownership |
|---|---|---:|---|---|
| `assignmentId` | string | Yes | Recommended deterministic `{contextId}_{memberUid}_{assignmentRole}` | Server |
| `organizationId` | string | Yes | Must equal parent organization ID | Server |
| `contextId` | string | Yes | Must reference same-tenant context | Server |
| `memberUid` | string | Yes | Active same-tenant member | Admin/owner |
| `assignmentRole` | enum | Yes | `contributor \| reviewer` | Admin/owner |
| `status` | enum | Yes | `active \| revoked` | Admin/owner |
| `assignedByUid` | string | Yes | Admin/owner member | Server |
| `createdAt` | timestamp | Yes | Immutable | Server |
| `updatedAt` | timestamp | Yes | Server timestamp | Server |

**Primary key:** `assignmentId`.  
**Foreign keys:** `contextId -> contexts.contextId`; `memberUid -> members.uid`; `assignedByUid -> members.uid`.  
**Unique rule:** one active assignment per context/member/role.

### 5.7 `organizations/{organizationId}/responses/{responseId}`

The central feedback record. It contains contributor content and is restricted by role, assignment, and visibility policy.

| Field | Type | Required | Allowed values / constraints | Ownership |
|---|---|---:|---|---|
| `responseId` | string | Yes | Must equal document ID; deterministic submission ID | Server/client-generated before idempotent create |
| `organizationId` | string | Yes | Must equal parent organization ID | Server |
| `contextId` | string | Yes | Existing same-tenant context | Server |
| `contributorUid` | string | Yes | Authenticated user on create | Server |
| `contributorDisplayName` | string/null | No | Snapshot only when visibility permits | Server |
| `rating` | integer | Yes | 1 through 5 inclusive | Contributor create; immutable MVP |
| `review` | string | No | Empty allowed; bounded, e.g. <= 4,000 chars | Contributor create; immutable MVP |
| `suggestion` | string | No | Empty allowed; bounded, e.g. <= 4,000 chars | Contributor create; immutable MVP |
| `status` | enum | Yes | `new \| in_review \| actioned \| archived` | Server/admin mutation |
| `assignedToUid` | string/null | No | Active permitted same-tenant member | Admin/owner |
| `createdAt` | timestamp | Yes | Server timestamp | Server |
| `updatedAt` | timestamp | Yes | Server timestamp | Server |
| `firstReviewedAt` | timestamp/null | No | Set once on first review | Server |
| `actionedAt` | timestamp/null | No | Set when actioned | Server |
| `archivedAt` | timestamp/null | No | Set when archived | Server |
| `lastStatusChangedByUid` | string/null | No | Active admin/owner | Server |

**Primary key:** composite logical key `organizationId + contextId + contributorUid`, materialized as `responseId`.  
**Foreign keys:** `contextId -> contexts.contextId`; `contributorUid -> members.uid`; `assignedToUid -> members.uid`.  
**Unique rule:** one response per context and contributor in MVP; reopening a context does not create a second response.

### 5.8 `organizations/{organizationId}/activity/{activityId}`

Append-only audit and internal-note records. Clients cannot overwrite or delete activity.

| Field | Type | Required | Allowed values / constraints | Ownership |
|---|---|---:|---|---|
| `activityId` | string | Yes | Must equal document ID | Server |
| `organizationId` | string | Yes | Must equal parent organization ID | Server |
| `responseId` | string/null | No | Required for response activity | Server |
| `contextId` | string/null | No | Required for context activity | Server |
| `actorUid` | string | Yes | Authenticated member who caused action | Server |
| `type` | enum | Yes | `status_changed \| assigned \| internal_note \| context_changed \| member_changed` | Server |
| `payload` | map | Yes | Typed, bounded, no unnecessary sensitive data | Server |
| `createdAt` | timestamp | Yes | Immutable server timestamp | Server |

**Foreign keys:** `responseId -> responses.responseId`; `contextId -> contexts.contextId`; `actorUid -> members.uid`.  
**Ownership:** permitted administrators/owners can read; contributors never read internal notes.

| Field | Type | Required | Constraints | Ownership |
|---|---|---:|---|---|
| `aggregateId` | string | Yes | `context_{contextId}` or `org_{period}` | Server |
| `organizationId` | string | Yes | Must equal parent ID | Server |
| `contextId` | string/null | No | Null for organization-wide data | Server |
| `periodStart` | timestamp/null | No | UTC inclusive | Server |
| `periodEnd` | timestamp/null | No | UTC exclusive | Server |

## 6. Relationships and Cardinality

| Relationship | Cardinality | Enforcement |
|---|---|---|
| User -> membership | 1 to many | Membership path and active status. |
| Organization -> members | 1 to many | Parent path; owner Function maintains one owner minimum. |
| Organization -> contexts | 1 to many | Parent path and matching organization ID. |
| Context -> questions | 1 to many | Parent path; fixed MVP question set. |
| Context -> assignments | 1 to many | Assignment references an active same-tenant member. |
| Member -> assignments | 1 to many | Query by member UID; rules validate tenant. |
| Context -> responses | 1 to many | Response context ID references same-tenant context. |
| Contributor -> responses | 1 to many | Contributor UID equals creator on create. |
| Response -> activity | 1 to many | Activity references response and same tenant; append-only. |
| Organization/context -> aggregates | 1 to many | Derived server-managed documents. |
| Organization -> invitations | 1 to many | Invitation references organization and expires. |

Firestore does not cascade deletes. Prefer soft states (`suspended`, `closed`, `archived`). Permanent deletion or anonymization must be an audited, privileged Function job.

## 7. Indexes and Query Requirements

Firestore automatically indexes individual fields. Add composite indexes only for actual query shapes.

| Collection path | Fields | Purpose |
|---|---|---|
| `contexts` | `status`, `updatedAt desc` | Admin context list. |
| `contexts` | `ownerUid`, `status`, `updatedAt desc` | Owner-scoped contexts. |
| `assignments` | `memberUid`, `status`, `contextId` | Assigned active contexts. |
| `responses` | `contributorUid`, `createdAt desc` | Contributor history. |
| `responses` | `contextId`, `createdAt desc` | Context response list. |
| `responses` | `status`, `createdAt desc` | Admin inbox status filter. |
| `responses` | `rating`, `createdAt desc` | Rating filter. |
| `responses` | `assignedToUid`, `status`, `createdAt desc` | Admin work queue. |
| `responses` | `contextId`, `status`, `createdAt desc` | Context/status drill-down. |
| `activity` | `responseId`, `createdAt desc` | Response activity history. |
| `activity` | `contextId`, `createdAt desc` | Context activity history. |
| `invitations` | `emailHash`, `status`, `expiresAt` | Invitation acceptance lookup. |

Query rules:

- Every organization query must include an organization path and/or equality constraint.
- Every list query must use a page size, cursor pagination, and explicit ordering.
- Do not load all responses to calculate a dashboard on every screen open.
- Firestore has no full-text search. MVP keyword search is limited or deferred to a separately approved search service.
- Real-time listeners are limited to active inbox/context views where freshness has clear value.

## 8. Authentication and Session Handling

### Authentication lifecycle

1. Initialize Firebase and subscribe to `authStateChanges`.
2. Let Firebase Auth restore a persisted session.
3. Obtain current ID tokens through the Firebase SDK; never store or manually manage refresh tokens.
4. Load the user profile and active membership after authentication.
5. Route missing profiles or memberships to onboarding; route suspended memberships to blocked access.
6. On sign-out, clear user-scoped providers, cached query state, local drafts, and navigation history.

### Authentication requirements

- MVP provider is email/password.
- Normalize email for comparison, but use Firebase Auth as identity authority.
- Create the profile through a trusted or tightly constrained operation after Auth account creation.
- Do not reveal whether an email exists during password reset or invitation lookup.
- Use Firebase protections for repeated failed sign-ins and monitor failures.
- Email verification is policy-controlled; if enabled, gate sensitive organization actions until verified.

### Token and role changes

- ID tokens are refreshed by the SDK.
- Membership documents are the Firestore Rules source of truth.
- If custom claims are used for routing, update them only from Admin SDK code and force refresh after role changes.
- A suspended member must lose access through Rules even if the UI is stale.
- Auth state changes or token errors route the app to sign-in without exposing protected content.

## 9. Permissions Matrix

`R` means read, `C` create, `U` update, and `D` delete. Permanent deletes are not client-enabled in MVP.

| Resource | Contributor | Reviewer | Administrator | Owner |
|---|---|---|---|---|
| Own user profile | R/U own | R/U own | R/U own | R/U own |
| Organization profile | R permitted | R permitted | R permitted | R/U |
| Memberships | R own | R own | R if policy allows | R/U/C via Function |
| Contexts | R assigned/active | R scoped | R/C/U permitted | R/C/U |
| Questions | R assigned | R scoped | R/U fixed set | R/U |
| Assignments | R own | R own scope | R/C/U permitted | R/C/U |
| Responses | C/R own | R permitted scope | R/U permitted | R/U |
| Activity | No internal notes | R only if explicitly granted | R/C permitted | R/C |
| Aggregates | No | R if dashboard granted | R | R |
| Invitations | No | No | C/R own organization | C/R/U |

### Field-level restrictions

- Contributors cannot set `status`, `assignedToUid`, timestamps, `organizationId`, `contributorUid`, or audit fields.
- Reviewers cannot read internal-note payloads unless a separate policy explicitly permits it.
- Administrators cannot change member roles or organization ownership unless the authorized Function permits it.
- Owners cannot bypass validation or the last-owner invariant.
- Client writes to aggregates, invitations, role changes, and activity are denied; use Functions.

## 10. Data Ownership Rules

### Tenant ownership

- The organization owns contexts, assignments, responses, activities, and aggregates created within its tenant.
- A user owns their profile and submitted response content, subject to retention and legal policy.
- Administrators manage operational status and assignments but do not rewrite contributor content.
- Internal notes belong to the organization and are visible only to authorized operational roles.

### Response ownership

- On create, `contributorUid` comes from `request.auth.uid` or trusted Function context.
- A contributor can read only responses where `contributorUid == request.auth.uid`.
- A contributor cannot change rating or text after submission in MVP.
- Admins update workflow metadata only; they cannot silently edit contributor content.
- The context must exist, be active, and be assigned to the contributor at creation time.
- Existing response visibility follows the context policy and role permissions.

### Cross-tenant protection

- A document path and its `organizationId` must agree.
- Every referenced member, context, assignment, and response must belong to the same organization.
- Never query a client-provided organization ID without checking active membership.
- Never expose a not-found versus permission-denied distinction for inaccessible resources.

## 11. Security Rules Requirements

Rules must default to deny and explicitly allow each operation. Test:

- Unauthenticated read/write to every collection.
- Contributor access to another organization or another contributor's response.
- Reviewer access outside assigned contexts.
- Administrator access outside permitted organization scope.
- Suspended member access.
- Attempts to alter immutable IDs, ownership, timestamps, status history, or aggregates.
- Response creation for paused, closed, or unassigned contexts.
- Duplicate response creation.
- Suspending or demoting the last owner.

Rules should use helpers such as `isSignedIn`, `isActiveMember(orgId)`, `roleAtLeast(orgId, role)`, `sameOrganization`, and `isUnchanged(field)`. Rules are not a substitute for Function validation or transaction integrity.

## 12. Transactions, Functions, and Invariants

Implement these as callable or HTTPS Functions using the Admin SDK:

- `createOrganization`: create organization and initial owner membership atomically.
- `acceptInvitation`: verify token hash, expiry, email policy, and create membership atomically.
- `inviteMember`: validate inviter role, target role, scope, and rate limits.
- `setMemberRole`: prevent last-owner removal and append activity.
- `createResponse`: validate context, assignment, uniqueness, and server fields transactionally.
- `transitionResponseStatus`: validate legal transition, update timestamps, and append activity atomically.
- `assignResponse`: validate assignee membership and append activity atomically.
- `addInternalNote`: validate role and bounded content, then append activity.
- `rebuildAggregates`: rebuild derived metrics from authoritative responses.
- `purgeExpiredInvitations`: scheduled, idempotent cleanup according to policy.

### Legal status transitions

```text
new -> in_review -> actioned -> archived
new -> archived
in_review -> archived
archived -> in_review (administrator/owner only, with audit record)
```

Invalid transitions return `failed-precondition`. A transition is never accepted solely because the client rendered a valid option.

## 13. API Contracts

The Flutter client uses repositories for ordinary CRUD and real-time reads. Callable Functions provide trusted boundaries for privileged or multi-document operations.

### Repository operations

```text
watchMembership(organizationId)
watchAssignedContexts(organizationId, memberUid)
watchOwnResponses(organizationId, memberUid, cursor)
watchInbox(organizationId, filters, cursor)
watchDashboardMetrics(organizationId, filters)
createDraftContext(input)
updateContext(contextId, patch)
createResponse(input, idempotencyKey)
```

All methods return typed domain results and map Firebase failures to stable codes: `unauthenticated`, `permissionDenied`, `invalidArgument`, `notFound`, `alreadyExists`, `failedPrecondition`, `offline`, and `unknown`.

### Callable contracts

| Function | Caller | Input | Output / side effects |
|---|---|---|---|
| `createOrganization` | Authenticated onboarding user | Organization name | Organization ID; owner membership. |
| `inviteMember` | Owner/admin by policy | Organization ID, email, role, optional scopes | Invitation ID and expiry; no account-existence disclosure. |
| `setMemberRole` | Owner | Organization ID, member UID, role | Updated membership and audit activity. |
| `acceptInvitation` | Authenticated invite recipient | Invitation ID, raw token | Active membership and invitation acceptance. |
| `transitionResponseStatus` | Admin/owner | Organization ID, response ID, next status | Updated response and activity record. |
| `rebuildAggregates` | Owner/operations | Organization ID, optional context ID | Rebuild result; audited invocation. |

Mutation requirements:

- Return the authoritative document or mutation result after commit.
- Return a stable, safe error code on failure.
- Never return stack traces, tokens, or data outside caller permissions.
- Use idempotency keys for response creation and retried multi-document operations.

## 14. Retention, Deletion, and Recovery

- MVP uses soft states instead of client-side hard deletion.
- Account deletion must define whether responses are deleted, anonymized, or retained before production.
- Organization deletion requires owner confirmation, authorization, an auditable job, and a recovery window if appropriate.
- Backups and exports follow the same access and retention policy as primary data.
- Aggregate documents are disposable and rebuildable; response documents are authoritative.
- Scheduled cleanup is idempotent and rate-limited.

## 15. Backend Acceptance Checklist

- All collections and subcollections exist in the Emulator Suite with seeded role fixtures.
- Rules tests cover unauthenticated, same-tenant, cross-tenant, wrong-role, suspended, and field-tampering cases.
- Response creation is idempotent and cannot duplicate one contributor/context pair.
- Context lifecycle rules prevent responses to paused or closed contexts.
- Status, assignment, invitation, role, and internal-note mutations are server-validated and audited.
- All list queries are bounded and have required composite indexes.
- Dashboard aggregates reconcile against seeded response data and do not show an average for zero responses.
- Logs and analytics exclude review text, suggestions, passwords, tokens, and unnecessary personal data.
- Staging and production Firebase projects have separate credentials, data, rules, and configuration.
- Backup, retention, account deletion, and data residency decisions are approved before production release.
